01 Overview & scope

Two storefronts sharing one workshop

A public store where visitors browse and buy handmade carpentry, and a private portal where the maker runs inventory, orders, and merchandising. Both are one Next.js app talking to one Supabase project, with Stripe handling money so we never touch card data.

In scope · v1

  • Public catalog with filter, sort & search
  • Cart, coupon entry & Stripe checkout
  • Order confirmation & status updates by email
  • Verified-purchase product reviews
  • Admin: products, stock, photos, pricing, tags
  • Admin: orders, coupons, sales/discounts, reviews
  • Standard pages: landing, about, contact, policies

Out of scope · v1 (parked)

  • Customer loyalty / points program
  • Multi-maker / marketplace accounts
  • Wishlists & back-in-stock alerts (stretch)
  • Full CMS for arbitrary page building
  • Native mobile app
  • International multi-currency (single currency v1)

05 Critical flows

The paths that must not break

The sequences where a bug costs money or trust. The purchase and inventory flows are the ones to build defensively.

1

Purchase & fulfillment

Money path
  1. Customer builds a cart (held client-side) and enters an optional coupon.
  2. At checkout, the server re-validates stock, prices, and the coupon — the client is never trusted for totals.
  3. Server creates a Stripe Checkout Session with verified line items and Stripe Tax; fulfillment is local pickup (no shipping calc at v1). Customer is redirected to Stripe to pay.
  4. Stripe fires checkout.session.completed to our webhook; we verify the signature.
  5. Webhook creates the order, writes line items, decrements stock, and stores the Stripe reference — all in one transaction.
  6. Confirmation email sent with pickup details (and a made-to-order lead time when any item is built to order); customer lands on a success page; order appears in the admin queue.
Guardrail · The order is born from the webhook, not the browser redirect, so a closed tab or flaky network never loses a paid order.
2

Inventory & concurrency

Oversell risk
  1. Two customers check out the last unit of a product at nearly the same time.
  2. Stock is decremented in a guarded DB transaction (conditional update: only if stock >= qty).
  3. The second webhook's decrement fails the condition and is flagged.
  4. That order is auto-refunded via Stripe and the customer is emailed an apology + restock note.
Decision · Decrement-on-payment (simple, tiny oversell window) vs. reserve-at-checkout (complex, needs expiry). Recommending decrement-on-payment for v1 given low volume.
3

Add / edit a product

  1. Admin opens the product form; fills name, description, price, stock, tags.
  2. Uploads photos to Storage; drags to set the display order.
  3. Optionally sets a sale price, toggles active, and flags made-to-order with a lead time.
  4. Save writes the product + images + tag joins; storefront reflects it immediately.
4

Leave a verified review

  1. After delivery, customer follows a review link tied to their order + product.
  2. System confirms that order actually contained that product (verified purchase).
  3. Review is saved as pending; admin approves or hides it from the moderation queue.
  4. Approved reviews show on the product page and update its aggregate rating.
5

Coupon redemption

  1. Customer enters a code in the cart; server checks validity, min-total, usage limit, expiry.
  2. Valid → discount is reflected and passed into the Stripe session as a real price reduction.
  3. On successful payment, the coupon's usage count increments with the order.

07 Open items & risks

What we need to settle

The parking lot — decisions to make as a group before their dependent phase. A few of these (shipping, especially) can reshape the plan, so they're worth an early call.

Logged

  • Hosting→ Vercel. Phase 0 spike hit a hard local build wall on Cloudflare's OpenNext adapter (workerd needs macOS 13.5+ or a modern glibc-linux container — unavailable on the dev machine as configured). Vercel builds natively, no extra tooling. Free Hobby tier through build; upgrade to Pro at go-live per Vercel's commercial-use terms.
  • Email provider→ Resend. Free tier covers volume; React Email fits the stack. Postmark is the fallback.
  • Shipping model→ Local pickup for v1. Schema kept shipping-ready so flat-rate or weight/zone can be added later.
  • Guest vs. accounts→ Guest checkout, minimal info. Account creation offered but optional.
  • Product variants→ One SKU per product. Sizes/versions listed separately; variants table dropped.
  • Made-to-order→ Per-product flag + lead time. Still stock-counted; longer fulfillment shown to buyers.
  • Tax & currency→ Stripe Tax, single currency.
  • Review policy→ Verified purchase + pre-moderation.
  • Inventory→ Decrement on payment. Guarded conditional update.

Risks to watch

  • Overselling one-of-a-kind stockHandmade goods are often quantity-one; the concurrency guard in Flow 2 matters more than for mass retail.
  • Shipping deferred, not gonePickup sidesteps freight for now — but revisit before adding shipping, since bulky items make flat-rate risky (see comparison).
  • Lead-time clarityMade-to-order pieces must show their lead time clearly, or buyers expect instant pickup.
  • Webhook reliabilityThe order pipeline hinges on it — needs retries, idempotency, and monitoring.
  • Single-admin bus factorOne owner running everything; keep the admin simple and document the runbook.
